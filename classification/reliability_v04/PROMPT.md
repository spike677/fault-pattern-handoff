# MECH-v0.4 从固定源码到根因

只使用随本次请求给出的原件和九条目录。逐案填写，覆盖全部 case_id。源行号以每段前缀为准。保留证据支持的作用域、条件和不确定性。每个动作以一句话分别写预期行为、固定旧版本的实际行为和被破坏的关系；每条事实说明引证如何支持判断。

1. 先确认版本、接口语义和执行分支。追踪目标参数、地址、计算项或状态的实际来源。
2. 找到首个可证违约，定位到具体读、判断、更新、存储或计算。说明下一处实际消费者，以及它怎样消费错误量。语义等价、合规默认和正确末端舍入按各自的适用范围记录。
3. 先定因果关系，再对照九张卡逐项提交必要事实、近邻证据和排除理由。从异常症状不能直接推出实现错误。可证明目录外时填写具体违约和 `established_other_defect`。根动作已经证明而叶级缺证时保留可靠的上位或未知。

## 节点与关系

- `root_action` 记录一个有证据的首个违约，`independent_action` 记录同一案例中有各自独立违约依据的动作。每个已证动作的 `implementation_action` 和 `causal_role` 都提供独立证明。多个根没有已证主次时，写出 `independent_of` 及双方的实际违约锚点。一处替换共同决定两个字段或多个影响时，以一个根记录。
- `downstream_effect` 记录另一个经过证明的局部失效关系，给出 `causes` 或 `propagates_to` 的根或上游。若模式描述该首错引起的局部失效，在根节点引用实际消费者并提交九卡事实。同一处实现缺陷只计一个根。
- `supporting_operation` 记录用于证明消费者或正确对照的正常操作。可从正常消费者用 `consumes` 指向产出其输入的节点，或用 `supports` 指向所支持的节点。正常消费使用空事实数组。举证可以直接使用正常消费者的同域旧代码。
- `unknown_action` 用于待证假设或合规边界。找不到首错时写清缺少的同版证据，并将未知位置留空。没有可证错误时仍提交这一节点。
- 各关系的 `from`、`to` 是同案节点 ID。`violates` 由已证动作连到其适用合同，`to` 填 `contract`。链路证据说明是哪个确切值、对象、构建或路径接起来，独立性说明修复另一动作后该违约为何仍成立。没有这样的证据就不画因果边。

## 先选作用域，再逐条装配证据

每个动作先比较静态域和报告域各自能支持哪些决定性事实，再选能闭合实际动作、机理细节和消费者的路径。把该路径的原件填入 `scope.source_id`。固定旧实现能在同域证明这些事实时，提交完整静态证明。报告只概述修复或效果时，按静态域提交旧实现中的已证细节。只有报告明确确认受评结论所需的细节时，才在报告域闭合该结论。其他版本的材料留在 `readback` 说明关联。

- 静态推导用 `derived`。**每条决定性事实的 `anchors` 内分别填写同版本的 `requirement` 和动作路径上的旧侧 `behavior`**。这也适用于 `applicable_contract` 本身、`implementation_action`、`causal_role`、决定性否定和消费者事实。多条事实依据同一合同或旧操作时，在每一条中重复相应锚点。合同可以来自同版的另一个文件；至少一个行为锚点要在所选动作路径。将动作位置压到旧实现的实际操作行。补丁新增行、标题、修复后通过及猜测不作为旧侧证明。
- 适用的数学关系可以由同版算法定义证明，包括归约循环的合法成员、顺序、权重和目标累加关系。引用给出该关系的代码作 `requirement`，引用实际读写及消费者作 `behavior`，并解释两者如何约束同一个受评操作。没有文字合同本身不构成静态缺证。未明确承诺的 dtype、误差界或舍入规则保留其假设范围。仅凭类型名、输出类型或修复后使用更宽类型，不能断言旧实现违约。
- 作者明确确认用 `confirmed_report`，在 `reported` 作用域内给每条事实引用该报告的 `confirmation`。只确认引文实际支持的合同、动作、机制、消费或角色。同一报告的引文可按需在各条事实中重复。缺一条决定性静态依据时，另一快照的报告不会替代它。若报告能独立证明该结论，应选报告路径并引用对应确认行。
- 合规或适用性边界可作为零根的 `unknown_action` 单独提交，按原件证实的内容选择 `compliant` 或 `contract_inapplicable`，对明确确认的报告边界在同域使用 `confirmed_report` 和 `confirmation` 而无需提交违约动作或因果事实，未证推测保留 `hypothesis`。
- 只展示源码一句、未归因现象或试验结果时为 `observation`，猜测为 `hypothesis`。 `verified_runtime` 需要同一次调用的 build、call_id、路径和 `runtime` 锚点。
- C1 证明确有不合资格的项被采用，C2 证明必需项确实被跳过，C3 证明同一逻辑来源对于同一目标被超额重复。只见读取状态、值相等或补丁移动操作时，追查实际消费者和合同。
- 对掩码，沿实际构造的资格位查到消费者，核清非法位置是不是被普通运算使用。因地址映射送错目标导致的遗漏或碰撞，先确认相应地址关系，参与模式需有自己成立的逻辑成员证据。对同名 helper 或重载，沿明确的传参和注册入口确认实际调用；接口级语义可以成立时保留这一范围。
- 合法允许省略的参数若被入口拒绝，核对参数上位条件与后续状态消费证据。对寻址，区分布局公式、元素到字节的单位换算、向量写入的硬件对齐与数值表示回绕。用本案具体的实际地址和访问证明差异。
- NUM-01 要为实际累加动作、相邻更新间同一槽的读取及窄存、失真传播和角色分别装配事实。对照保持同项、同序、同权并复算首个丢失的差异，定位下一次更新或末端向宽类型的实际消费。明确合同允许的逐次舍入、仅在末端转换和单项先失真各自适用的范围。
- NUM-02 分别记录原件所证的两种公式与实际归一化消费者、在指定同精度下可复算的数学对照、以及该对照对目标工作精度的适用证据。自行计算写在 `readback`，列出输入、精度、舍入和有限的平方，保留公式级报告原有的确认范围。若决定性同精度对照无法绑定受评路径，保留该缺项。不以另一快照测试的类型或更高精度的中心式填补。同版实际类型链可用静态证据证明。

提交前按每张相关卡的必要事实列表扫一遍。对每个决定性事实单独看它的锚点，核对源 ID、版本、用途和行范围，再查实际消费者以及根数。若缺口只能支持上位或缺证，写清缺项。`readback` 简述语义链、最近竞争解释及旁证。每案至少给出一个动作、未知或边界节点，返回规定的 JSON。
