# 原件读件与动作记录 v0.4.2

沿用下文的七条冻结目录和数值候选判据。以下规则明确证据等级和动作的输出位置。逐案用适用合同、旧路径和实际消费者定位首错，说明适用条件和证据缺口。允许有据排除、缺证或多个独立动作。

## 断言和锚点

| claim_state | 填写条件 |
| --- | --- |
| `observation` | 原件直接显示的代码、数值或陈述。引用精确行范围。直接看到一条语句，只能证明这条语句出现。 |
| `hypothesis` | 作者猜测、补丁效果或静态链条中缺失的条件。注明缺什么。 |
| `derived` | 结合适用合同、同版本旧行为和必要消费者得出的结论。引用合同为 `requirement`、动作作用域内旧代码为 `behavior`，其他旧路径的消费者可作 `context`。在 `explanation` 写清从这些锚点推出违约的步骤。 |
| `confirmed_report` | 作者明确确认原始动作和适用范围。以同作用域的报告原句作 `confirmation`，保留作者的范围和语气。 |
| `verified_runtime` | 该运行确实经过给定路径，原件绑定相同的 `build` 和 `call_id`。引用 `runtime` 行。 |

`implementation_action` 表达被裁决的实际错误动作。若由源码推导，给这条事实本身设置 `derived`、推导说明和完整锚点。单独在另一事实写出推导不能替代这条动作事实。对于 `applicable_contract`、`established_other_defect`、`causal_role` 和候选决定性事实，也分别填写各自所需的证据。同一个锚点可以在多条事实中承担不同作用。补丁新增行、通过结果、作者猜测或合理性判断不能单独成立为旧路径违约。无法完成证明时保留未知因果角色和缺证，写出待核条件。

举例。仅看见一个值在代码中转型是观察。在已证明该路径承诺保留输入中的整数位置、旧存储宽度造成位置碰撞且旧读取方确实消费该位置的情况下，“旧实现保存了错误位置”是静态推导。若原件只显示更新存储宽度后测试通过，则继续核对原存储和消费链。

## 动作与正常操作

- `actions` 记录被裁决的错误动作或待证候选。首错是根动作，使用有据的 `primary` 或 `independent`。多个有据独立动作且原件未排主次时，使用多个 `independent`，各自提供违约依据。
- `downstream` 记录自身已证明违反可陈述约定、由已知上游动作造成的失效关系。填 `upstream_id` 和有据的 `causal_role`。上游输出错误导致最终数值错本身不足以再列一条。若下游动作即使当前一个根因修复仍独立违约，请单列独立根动作。
- `supporting_operations` 记录用于证明实际消费的正常转宽、正常归约、尺度计算、写回等。填对应根动作的 `action_id`、简述和同版本的原件锚点。在根动作事实中保留判定所需的消费引证和推导，例如 `distorted_value_consumed`。正常动作只放在支持数组，数组可为空。

提交前逐个检查 `actions` 项是否有自己的违约或明确的待证候选，根动作证据等级是否和锚点一致，正常消费者是否归回对应动作，以及每个独立错误是否都保留。只输出符合响应 schema 的 JSON。
