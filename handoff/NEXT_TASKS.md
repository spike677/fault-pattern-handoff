# fault_pattern 接手计划

2026-11-15，北京时间｜阶段性交接与下一轮范围

本地现有 Work 已完成 P0 审查、P1 设计和四份交接资料。`fault_pattern` 用于分类设计和研究决策，新的 Work 复核和验证，Codex「精度」维护工程、代码、测试及历史。交接单位为可复核的研究结论和工程版本。[工程状态](./PROJECT_STATE.md) · [分类设计](./CLASSIFICATION_DESIGN.md) · [检查记录](./WORK_REVIEW.md)

## 交接顺序

1. **审阅本地交接件。** 核对已确认、暂定和待验证事项。先决定哪些结论、路径及原始引用可进入 `fault_pattern` 的共享范围；内部原件及证据保留在获准环境。同步文件清单记录用途、来源版本、脱敏位置和批准范围。
2. **确认 GitHub 交接目标。** 用户指定经批准的私有仓库和可同步的文件。当前 FaultAudit `origin` 为公开仓。另一次授权后的 Codex 操作可在批准的目标工作树用文件清单准备提交，记录仓库、分支、完整提交 SHA 及四件资料的内容标识。旧源码版本及当前交接提交分别标注。
3. **在旧 ChatGPT Project 核验访问。** 用户完成所选 GitHub 仓的授权后，在 ChatGPT Project `fault_pattern` 用审核确认的提交读取 `handoff/PROJECT_STATE.md` 和 `handoff/CLASSIFICATION_DESIGN.md`。要求返回读取的提交、两个路径及一条带证据的结论。访问实测结果单记，并保留本地对应版本作为工作凭据。
4. **在 `fault_pattern` 启动下一轮 Work。** 发出仓库/分支/完整 SHA 及下面的核查任务。如果桌面 Work 能访问本地工程，可先验证实际目录为 `D:\project\精度`，再读取本地 `handoff/` 并对读已提供的固定版本。保留证据、测试条件和未知项，输出可复审的结果。

## 下一轮 Chat 的决策

- 确认机制分类单位和适用范围。对照原 30 的重名条目，决定参考错、合同允许差异、已证破坏动作与产品合同待证怎样呈现。
- 审阅 A–D 和计划消费的边界。优先确认有效集与贡献重数、块参与轮次与共享槽生命期、Host 计划与设备实收及消费的判别条件。
- 确认独立评估可接受的证据与阈值。已知根因事后分类和未知根因诊断分别定规则，指标含正确机制、误强归因、弃权及同预算定位。评估方向锁定后再接触留出数据。[分类草案](./CLASSIFICATION_DESIGN.md)

## 下一轮 Work 的验证

- **先对版本。** 记录本机可读目录、实际打开的文件、仓库/分支/提交、可见资料和缺项。优先找带来源锚点的冻结 `declared_details`，同时核对 `catalog_scope`、30 条原始行和实际模式 ID。暂缺产物时，可从固定原表继续做开发近邻比较。
- **P1 最小验证。** 起草五张规则卡，覆盖 A–D 和计划消费。用八个已见子问题做桌面校准。04、12、07、08 给出四条候选的判别证据，01 核对计划与消费，06 查参考错误，09 查允许差异，15 查合同与因果待证。07/08 作为同一事件家族。每项交付必要谓词、支持/排除/未知、来源锚点和下一观察。另设一项纸面对照检查多机制或证据冲突能否如实保存。
- **P2 独立验证。** P1 规则和预算审阅后，锁定两组互斥的未见事件家族，分别做事后分类和未知根因诊断。按 Issue、补丁、衍生用例和重复原件整组排除泄漏。输出分子与分母、错误归因、合理弃权、多机制漏报和取证成本。确认 P2 结果后再正式映射原 30。[P0–P1 审查原报告](<../算子精度故障模式库_P0-P1设计审查_20261115.md>)
